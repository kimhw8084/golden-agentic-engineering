# Capability selection research

Updated 2026-11-20 from current public repository metadata, official READMEs, licenses, and official product docs. The machine-readable review is [`capability-selection.json`](capability-selection.json). Each candidate is pinned to an observed main-branch commit so the evidence can be rechecked. Main-branch pins are not signed vendor releases.

## Decisions for this starter

- Keep OpenCode's native primary agent and existing lazy-loaded specialists/skills as the routine runtime. OpenCode documents skill loading as on demand, and MCP tools add model context; use only task-relevant capabilities. This is a design choice, **not** an internal-company benchmark result. See the [OpenCode skills guide](https://opencode.ai/docs/skills/) and [MCP guide](https://opencode.ai/docs/mcp-servers/).
- For OpenCode plugin/hooks, evaluate [`affaan-m/ECC`](https://github.com/affaan-m/ECC/tree/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7) as a serious public candidate. The pinned repo-level license is MIT; ECC's README describes the OpenCode plugin as beta, requires npm dependencies/build, and says it does not provide full feature parity. The integration offers lifecycle hooks and custom tools, which need a complete per-hook permission, prompt-injection, dependency/NOTICE, and offline review. Keep Golden's native task-scoped skills as the current choice; do not vendor the broad catalog or enable persistent hooks without matched runtime evidence.
- Keep [`cathrynlavery/diagram-design`](https://github.com/cathrynlavery/diagram-design/tree/d74d8c2d0c78a9e1efd43137f6a9a51182a8b5f0) first in line for an isolated diagram-task evaluation; it was missing from an earlier summary, not from the registry. At the pinned commit, the root [MIT license](https://github.com/cathrynlavery/diagram-design/blob/d74d8c2d0c78a9e1efd43137f6a9a51182a8b5f0/LICENSE) was verified. The skill tree has 321 files (5.86 MB), including 70 reference files and 8 scripts, and describes 51 visual types. The [privacy note](https://github.com/cathrynlavery/diagram-design/blob/d74d8c2d0c78a9e1efd43137f6a9a51182a8b5f0/PRIVACY.md) says it has no server, accounts, analytics or telemetry; source review also found default Google Fonts requests and optional web onboarding. Onboarding asks before fetching URLs and permits local references. A system-font/offline mode exists, but default runtime is not zero-egress compliant; the offline mode, scripts and Playwright/Chromium export dependencies have not been executed or staged. Windows/Linux behavior, full dependency/NOTICE closure, prompt-injection safety and diagram output quality remain unverified. Its first-project style questions may add overhead; no matched time/quality trial exists. Do not vendor or make it the team default yet. Mermaid/SVG is the current offline fallback while an isolated, no-egress, cross-platform evaluation is prepared.
- For React design, [`nextlevelbuilder/ui-ux-pro-max-skill`](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/tree/2de1134dc4d1cfe112934611ae5803ae17a1bd7e) is the first external skill to evaluate. The exact pinned source includes an MIT license; the complete searchable data, helper scripts, dependency/license closure, prompt-injection surface and offline behavior have not been audited. Keep the in-repo `golden-react` skill and approved company design system as the usable path while review is incomplete.

The initial jsdom graph included `mdn-data` (CC0-1.0) and `caniuse-lite` (CC-BY-4.0); the OSI does not recommend CC0 for software, and the fixture's strict OSI-only dependency policy excludes that tree. [happy-dom 21.0.4 package metadata](https://www.npmjs.com/package/happy-dom/v/21.0.4) declares MIT and Node >=20. The replacement passed typecheck, six component/logic tests and a Vite build on macOS arm64 after an offline reinstall. Its audit covers 82 installed packages but still has four missing license-text files and 50 unstaged OS/CPU variants; this is not company approval, a browser test, or a Windows/Linux result. See the generated [dependency audit](react-macos-arm64-dependency-audit.json) and [CycloneDX SBOM](react-macos-arm64.cdx.json). The license policy is grounded in the [OSI approved list](https://opensource.org/licenses) and [OSI CC0 guidance](https://opensource.org/faq).

## Limits and next research work

This is a **targeted leading-candidate review** across skills, OpenCode plugins, agents/frameworks, MCP servers/development tools, browser tools, deterministic CLIs, and evaluation. It does not claim to enumerate every public GitHub project. It does not establish complete source-level security, transitive licenses, company import approval, Windows/Linux behavior, no-egress behavior, or capability performance. Public metadata and docs can change. No candidate from this matrix was installed or invoked as part of a company OpenCode session. No relative task score is reported because the internal runtime and approved test workloads are unavailable.

The current OpenCode plugin API also exposes server, TUI, GUI, and RPC parts through a dedicated plugin package ([official plugin docs](https://opencode.ai/docs/build/plugins/)). Golden currently does not need a custom lifecycle plugin to route its files and commands. A future hook should be added only for a proven gap, then reviewed and tested against the exact installed company version; public docs alone do not establish compatibility.

Before selecting any candidate for a company pilot, complete the `required_before_import` checklist in the JSON registry and test the top options against identical acceptance criteria. Keep direct OpenCode routing as the lightweight default until actual evidence supports adding a router, specialist, framework, MCP server, browser tool, or additional ceremony.
