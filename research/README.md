# Capability selection research

Updated 2026-11-21 from current public repository metadata, official READMEs, licenses, and official product docs. The machine-readable review is [`capability-selection.json`](capability-selection.json). Each candidate is pinned to an observed main-branch or stable release commit so the evidence can be rechecked. A commit pin is not itself a signed vendor release.

Each public candidate now has a `capability_type` so teams can filter skills, OpenCode plugins, workflows, frameworks, browser tools, MCP servers/SDKs, evaluators, application libraries, analytics engines, and deterministic CLIs without flattening them into a CLI catalog. [`schemas/capability-selection.schema.json`](../schemas/capability-selection.schema.json) defines the candidate fields and controlled types; `scripts/validate_manifests.py` checks required evidence, type membership, and full commit pins using only Python's standard library.

## Decisions for this starter

- Keep OpenCode's native primary agent and existing lazy-loaded specialists/skills as the routine runtime. OpenCode documents skill loading as on demand, and MCP tools add model context; use only task-relevant capabilities. This is a design choice, **not** an internal-company benchmark result. See the [OpenCode skills guide](https://opencode.ai/docs/skills/) and [MCP guide](https://opencode.ai/docs/mcp-servers/).
- The project config selects `golden-engineer` through OpenCode's documented `default_agent` field for new sessions. This makes the agent prompt active when the project opens in a compatible public build; the company's internal build and its precedence/permissions remain untested. Clear small fixes use the primary agent directly with no mandatory skill load.
- For OpenCode plugin/hooks, evaluate [`affaan-m/ECC`](https://github.com/affaan-m/ECC/tree/3f14a103a8694e51c1df9a806217a6d0b5f7a6f7) as a serious public candidate. The pinned repo-level license is MIT; ECC's README describes the OpenCode plugin as beta, requires npm dependencies/build, and says it does not provide full feature parity. The integration offers lifecycle hooks and custom tools, which need a complete per-hook permission, prompt-injection, dependency/NOTICE, and offline review. Keep Golden's native task-scoped skills as the current choice; do not vendor the broad catalog or enable persistent hooks without matched runtime evidence.
- The pinned [`cathrynlavery/diagram-design`](https://github.com/cathrynlavery/diagram-design/tree/d74d8c2d0c78a9e1efd43137f6a9a51182a8b5f0) review found a useful agentic design method and a root [MIT license](https://github.com/cathrynlavery/diagram-design/blob/d74d8c2d0c78a9e1efd43137f6a9a51182a8b5f0/LICENSE). A bounded audit inspected the core skill, plugin manifest, privacy and third-party license notices, statically scanned 71 Markdown files and 8 Python helpers without executing them, and checked archive paths/types. It also confirmed default Google Fonts requests, optional URL onboarding, a Read/Write plugin manifest, optional Playwright/Chromium PNG export, and a mixed asset inventory that includes CC0 icons and third-party marks. The upstream style gate and review pause may add overhead; no output-quality/time comparison or company runtime trial has run. Golden adapts only the compact semantic-pattern-first, deletion-first and bounded-density methods in its existing offline `golden-docs` skill. Full upstream code, templates, scripts and icon assets remain `EVALUATION_ONLY_NOT_APPROVED`; see [`diagram-design-audit.md`](diagram-design-audit.md). Mermaid/SVG source remains the offline and diffable path.
- For React design, the pinned [`nextlevelbuilder/ui-ux-pro-max-skill`](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/tree/2de1134dc4d1cfe112934611ae5803ae17a1bd7e) source received a bounded review of core UI/design-system skills and CLI install/update paths. ## Limits and next research work

This is an **expanded but still targeted candidate review** across skills, OpenCode plugins, agent frameworks, MCP servers/development tools, browser agents, deterministic tools and evaluation. It does not claim to enumerate every public GitHub project. It does not establish complete source-level security, transitive licenses, company import approval, Windows/Linux behavior, no-egress behavior, or capability performance. Public metadata and docs can change. No candidate from this matrix was installed or invoked as part of a company OpenCode session. No relative task score is reported because the internal runtime and approved test workloads are unavailable.

The current OpenCode plugin API also exposes server, TUI, GUI, and RPC parts through a dedicated plugin package ([official plugin docs](https://opencode.ai/docs/build/plugins/)). Golden currently does not need a custom lifecycle plugin to route its files and commands. A future hook should be added only for a proven gap, then reviewed and tested against the exact installed company version; public docs alone do not establish compatibility.

Before selecting any candidate for a company pilot, complete the `required_before_import` checklist in the JSON registry and test the top options against identical acceptance criteria. Keep direct OpenCode routing as the lightweight default until actual evidence supports adding a router, specialist, framework, MCP server, browser tool, or additional ceremony.
